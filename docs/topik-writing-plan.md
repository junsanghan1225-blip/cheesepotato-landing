# TOPIK 쓰기 — 설계와 AI 채점 계획

작성 2026-08-12. 아직 코드는 없다. 무엇을 만들지와 **AI를 어디에 쓸지**를 정한다.

---

## 0. 왜 이 섹션은 다른가

지금까지 만든 것은 전부 **답이 정해져** 있다. 고르기는 보기 안에 답이 있고,
빈칸은 정답 문자열이 있고, 문장 만들기는 허용 답 목록이 있다. 그래서 채점이
규칙으로 된다.

**TOPIK 54번은 600~700자짜리 논술이다.** 규칙으로는 채점할 수 없다. 이것이
이 저장소에서 처음으로 **AI가 없으면 성립하지 않는 기능**이다.

거꾸로 말하면, 지금까지 AI를 안 쓴 것은 옳았다. 문장 만들기를 Gemini로
채점했다면 돈과 지연을 쓰고도 규칙보다 못했을 것이다.

---

## 1. 시험이 어떻게 생겼나

TOPIK II 쓰기는 문항 넷, 50분, 100점이다.

| 문항 | 무엇 | 분량 | 배점 |
|---|---|---|---|
| 51 | 실용문(안내문·이메일 등)의 빈칸 두 곳 | 각 한 문장 | 10 |
| 52 | 설명문의 빈칸 두 곳 | 각 한 문장 | 10 |
| 53 | 자료(도표·그래프) 보고 설명하기 | 200~300자 | 30 |
| 54 | 주제 하나로 논술 | 600~700자 | 50 |

### 채점 기준

51·52는 빈칸 하나에 5점이고 세 가지를 본다 — **내용이 맥락에 맞는가 ·
문법과 어휘가 정확한가 · 문체(격식)가 글 전체와 맞는가.** 셋째가 학습자가
가장 많이 놓치는 자리다. 안내문에 해요체를 쓰면 내용이 맞아도 깎인다.

53·54는 세 항목으로 나뉜다.

| 항목 | 53번 | 54번 | 무엇을 보나 |
|---|---|---|---|
| 내용 및 과제 수행 | 7 | 12 | 주어진 과제를 다 했는가, 주제에서 벗어나지 않았는가 |
| 글의 전개 구조 | 7 | 12 | 문단이 나뉘고 이어지는가, 접속이 자연스러운가 |
| 언어 사용 | 16 | 26 | 문법·어휘의 정확성과 **다양성**, 문어체를 지켰는가 |

**언어 사용이 절반을 넘는다.** 그런데 학습자는 내용을 채우는 데만 신경 쓴다.
이 섹션이 알려 줘야 할 것이 바로 그 비중이다.

---

## 2. 만들 것

배우기의 네 번째 갈래로 넣는다 — 코스 · 예문 · 문제 · **쓰기**.

```
배우기 › 쓰기 › [51] [52] [53] [54]
                 ↓
        문제 보기 → 원고지에 쓰기 → 채점 받기
```

### 화면에 반드시 있어야 할 것

1. **글자 수 세기.** 실시간으로. 600자와 700자에 눈금을 둔다.
   분량 미달은 실제 시험에서 가장 흔한 감점이고, 다 쓰고 나서
   세어 보는 것으로는 늦다.
2. **원고지 규칙 안내.** 문단 첫 칸 들여쓰기, 마침표 자리. 감점 요인이다.
3. **시간.** 54번은 30분이 권장 배분이다. 켜고 끌 수 있게 한다 —
   처음 쓰는 사람에게 타이머를 강제하면 안 쓴다.
4. **문어체 경고.** `-아/어요`, `저는`, `~인 것 같아요` 가 보이면
   그 자리에서 표시한다. 이건 **AI 없이 규칙으로 된다.** 논술에서
   해요체는 무조건 감점이라 규칙이 틀릴 일이 없다.

### 단계

| 단계 | 무엇 | AI |
|---|---|---|
| 1 | 문항·원고지·글자 수·타이머·문어체 경고 | 없음 |
| 2 | 51·52 규칙 채점 (허용 답 + 진단) | 없음 |
| 3 | 53·54 AI 채점 | Gemini |
| 4 | 쓴 글 저장하고 다시 보기 | 없음 (DB) |

**1단계만으로도 쓸 만하다.** 분량을 맞춰 시간 안에 쓰는 연습은 채점 없이도
가치가 있고, AI가 안 붙어도 섹션이 죽지 않는다. `score-pronunciation` 이
아직 미배포인 채로 발음 테스트가 돌아가는 것과 같은 구조로 짠다.

## 3. AI를 어디에 쓰나

### 쓸 곳

**53·54의 채점과 첨삭.** 규칙으로 안 되는 유일한 자리다.

그중에서도 값어치는 **점수가 아니라 첨삭**에 있다. "42점"은 학습자가
할 일을 알려 주지 않는다. "이 문장은 `-는 바람에`가 아니라 `-느라고`입니다 —
본인이 한 일이니까요" 는 알려 준다. 그리고 그건 학습자가 다른 데서 못 얻는다.

### 안 쓸 곳

- **51·52** — 답이 짧고 유형이 좁아 규칙이 낫다. 빠르고, 공짜고, 늘 같다.
- **문어체 검사** — `-아/어요`는 정규식이 잡는다. AI에 물으면 느리고 비싸고
  가끔 틀린다.
- **글자 수** — 말할 것도 없다.

**규칙으로 되는 것을 AI에 넘기지 않는다.** 이건 취향이 아니라 비용과
일관성의 문제다. 같은 글을 두 번 넣었을 때 점수가 달라지면 학습자는
채점을 안 믿는다.

---

## 4. Gemini 를 두 자리에 쓴다 — 자리가 다르다

**Gemini Spark 는 채점기가 아니다.** `gemini.google.com/spark/` 에서 도는
어시스턴트라 Workspace(문서·메일·일정)를 다루고 백그라운드로 일을 돌린다.
Edge Function 이 HTTP 로 부를 수 있는 API 가 아니다. 웹앱에 로그인해서
쓰는 것이라 학습자의 브라우저에서 채점을 시킬 방법이 없다.

그래서 **자리를 나눈다.**

| 자리 | 무엇이 | 무엇을 |
|---|---|---|
| **런타임 채점** | Gemini **API** (`gemini-3.6-flash`) | 학습자가 글을 내면 그 자리에서 채점·첨삭 |
| **만드는 쪽** | Gemini **Spark** | 문항 초안, 예시 답안, 운영 브리핑 |

런타임은 §4-1 그대로 간다. Spark 는 §4-2 다.

### 4-1. 런타임 — Edge Function + Gemini API

지금 저장소가 이미 쓰는 길을 그대로 늘린다.

```
브라우저 → Supabase Edge Function → Gemini
           (service_role 로 사용량 확인)
```

`recognize-word` 가 `gemini-3.6-flash` 를 `v1beta/interactions` 로 부르고,
`ai_usage` 표가 사용자별 하루 한도를 건다. **키는 함수 안에만 둔다** —
브라우저에서 Gemini를 직접 부르면 API 키가 페이지에 노출된다.

#### 새 함수 `score-writing`

받는 것 : `{ q: 53|54, prompt_id, text }`
주는 것 : 아래 모양의 JSON

```jsonc
{
  "scores": {                    // 공식 기준 그대로
    "content":   { "got": 9,  "max": 12, "why": "…" },
    "structure": { "got": 7,  "max": 12, "why": "…" },
    "language":  { "got": 18, "max": 26, "why": "…" }
  },
  "total": 34,
  "corrections": [               // 이게 본체다
    { "was": "공부하는 바람에", "now": "공부하느라고",
      "why": "본인이 한 일이라 -느라고입니다. -는 바람에는 돌발입니다." }
  ],
  "register": ["-아/어요 3곳 — 논술은 -(느)ㄴ다체"],
  "next": "문단을 셋으로 나누고 각 문단 첫 문장에 주장을 두세요."
}
```

#### 점수를 흔들리지 않게 하는 세 가지

1. **기준을 프롬프트에 통째로 넣는다.** "TOPIK 기준으로 채점해" 라고만 하면
   모델이 자기가 아는 대로 매긴다. 표를 그대로 붙인다.
2. **닻이 될 예시 답안을 같이 준다.** 상·중·하 세 편과 그 점수. 예시 없이
   숫자만 요구하면 같은 글에 매번 다른 점수가 나온다.
3. **temperature 를 낮게(0.2) 두고 JSON 스키마를 강제한다.**

그래도 **같은 글을 두 번 넣으면 점수가 조금 다를 수 있다.** 그건 숨기지 말고
화면에 적는다(§5).

#### 비용과 한도

54번 한 편은 넣는 글 700자 + 기준·예시 프롬프트라 대략 2~3천 토큰,
답이 1천 토큰쯤이다. `recognize-word` 한 번보다 훨씬 무겁다.

그래서 **사용량을 따로 센다.** `ai_usage` 에 얹지 않고 칸을 나눈다 —
단어 인식 30번과 논술 채점 3번은 같은 무게가 아닌데 한 칸으로 세면
둘 중 하나가 부당하게 막힌다.

```sql
alter table public.ai_usage add column if not exists writing_count integer not null default 0;
```

하루 몇 편으로 할지는 실제 토큰을 재 보고 정한다. 처음에는 **3편**으로
좁게 열고 늘리는 편이 안전하다. 무료 한도는 키 하나에 붙어 있어서 한
사람이 다 쓰면 전원이 멈춘다.

### 4-2. 만드는 쪽 — Spark 가 실제로 값어치 있는 자리

Spark 의 기능 넷 가운데 이 프로젝트에 걸리는 것은 **문서 만들기**와
**정기 브리핑**, 그리고 **다른 도구와의 분업**이다. 이건 학습자에게 가는
기능이 아니라 **우리가 만드는 속도**를 바꾼다.

**① 문항 만들기 (가장 급한 자리).**
§6 대로 기출문제를 그대로 못 쓴다. 51~54번을 유형만 같게 새로 써야 하는데
문항 하나가 지문·조건·모범답안 묶음이라 손이 많이 간다.

```
Claude(저)  문항 얼개와 채점 포인트를 저장소에 spec 으로 씀
   ↓        (유형·글자수·꼭 들어가야 할 문법·감점 요인)
Spark       그 spec 을 받아 Google Docs 에 문항 초안 여러 벌
   ↓
사람        Docs 에서 검토·수정 (한국어 선생님과 같이 보기 좋다)
   ↓
Claude(저)  확정본을 저장소 데이터로 넣고 검사기에 태움
```

Spark 안내문의 「Claude에서 생성한 아이디어·번역문·기획안 텍스트를 전달하여
Google Docs 에 문서화」가 정확히 이 길이다.

**② 채점 닻이 될 예시 답안.**
§4-1 에서 상·중·하 예시 답안이 있어야 점수가 흔들리지 않는다고 적었다.
54번 예시 한 벌은 600~700자짜리 글 셋 + 각각의 점수와 근거다. Spark 로
Docs 에 뽑아 두고 사람이 다듬는 편이 낫다 — 이건 코드가 아니라 글이라
저장소보다 문서에서 고치는 것이 빠르다.

**③ Skill 로 형식을 고정한다.**
Spark 의 「개인 맞춤 지침(Skill)」에 문항 형식과 우리 말투를 등록해 두면
매번 설명하지 않아도 같은 모양으로 나온다. 등록할 것:

- 문항은 `{ 유형, 지문, 조건, 모범답안, 채점 포인트, 감점 요인 }` 여섯 칸
- 예시 답안은 상·중·하 셋을 한 벌로, 각각 점수와 근거를 붙일 것
- **기출 지문을 그대로 옮기지 말 것** — 유형만 같게 새로 쓸 것

셋째 줄이 중요하다. 저작권은 나중에 고치기 어려운 문제다.

**④ 정기 브리핑.**
테스터 모집(6/12)과 배포 상태는 코드로 못 푸는 일인데 자꾸 잊힌다.
주 1회 요약을 받아 두면 챙길 수 있다.

### Spark 에 맡기지 않을 것

- **학습자 채점** — API 가 아니라 못 한다. 되더라도 사용자 계정으로 도는
  어시스턴트에 남의 글을 넣는 구조는 안 된다.
- **저장소 코드 수정** — 여기는 검사기와 커밋 이력이 지키는 자리다.
- **문항 최종 확정** — 초안까지다. 시험 문항이 틀리면 학습자가 틀린 것을
  배운다. 사람이 봐야 한다.

## 5. 넘지 말아야 할 선

**AI 점수를 TOPIK 점수라고 말하지 않는다.**

이 섹션을 쓰는 사람은 실제 시험을 준비한다. "당신의 쓰기 점수는 34점입니다"
라고 쓰면 그 숫자를 믿고 시험장에 간다. 실제 채점은 사람이 하고, 우리 점수와
다르다.

화면에는 이렇게 적는다 — **"연습용 참고 점수입니다. 실제 TOPIK 채점과 다를
수 있어요."** 그리고 점수보다 첨삭을 크게 보여 준다. 숫자를 작게 두는 것은
디자인 취향이 아니라 이 기능이 거짓말을 하지 않게 만드는 장치다.

같은 이유로 "합격 예상" 같은 말은 넣지 않는다.

## 6. 먼저 확인해야 할 것

- **문항을 어디서 가져오나.** 기출문제는 저작권이 있다. TOPIK 기출을 그대로
  올리면 안 된다. **같은 유형으로 새로 쓴 문항**을 만들어야 한다.
  이건 코드 문제가 아니라 콘텐츠 문제이고, 시작 전에 정해야 한다.
- **`score-pronunciation` 이 아직 미배포다.** 발음 AI도 안 올라간 상태에서
  새 함수를 하나 더 만들면 미배포가 둘이 된다. 순서를 정하는 편이 낫다.
- ~~"Gemini Spark" 가 무엇인지~~ → 확인됨(2026-08-12). Workspace 를 다루는
  어시스턴트지 API 가 아니다. 런타임 채점은 지금 쓰는 Gemini API 를 그대로
  쓰고, Spark 는 문항과 예시 답안을 만드는 쪽에 쓴다. §4 참고.
- **51~54번 문항을 몇 벌 만들 것인가.** 한 벌(넷)로 시작해 결을 보고 늘리는
  편이 낫다. 문항이 늘면 예시 답안도 같이 늘어난다.
