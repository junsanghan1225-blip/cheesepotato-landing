# 안티 그래비티 작업 지시 — TOPIK 듣기 120문항 (I 60 · II 60)

> 이 파일 전체를 안티 그래비티에 붙여 넣는다. (2026-10-03, `docs/plan-2026-q4.md` 2번)

## 왜

TOPIK 점수의 절반이 듣기인데, 사이트의 듣기 문항은 **45개뿐**이다(I 28 · II 17 — 읽기는 814).
모의고사 · 레벨 테스트 · 오늘의 TOPIK 이 같은 문항을 돌려 쓴다. 이번에 **TOPIK I 60 · TOPIK II 60** 을 더한다.

소리는 지금 녹음하지 않는다. 사이트가 `script` 를 브라우저 목소리로 읽는다(남 · 여는 높낮이를 갈라 읽는다).
그래서 **who(m · w · n)를 한 줄도 틀리면 안 된다** — 「여자는 무엇을 합니까」인데 여자 줄이 남자로 적히면 문제가 풀리지 않는다.

## 꼭 지킬 것

1. **기출이 아니다.** 실제 TOPIK 대본 · 문항을 옮기거나 조금 바꿔 쓰지 않는다. 유형만 따르고 대본 · 발문 · 보기 · 해설은 전부 새로 쓴다.
2. **사실을 지어내지 않는다.** 실제 기관 이름 · 전화번호 · 법 · 제도 · 통계 숫자 · 연구 결과를 사실처럼 쓰지 않는다.
   필요하면 「우리 동네 도서관」 「한 회사」처럼 일반으로 쓴다. (「~라는 연구가 있다」 같은 말도 쓰지 않는다.)
3. **모양은 `topik-listening.js` 의 문항 그대로.** 먼저 파일 맨 위 설명과 `lI-01` · `lI-17` · `lI-25` · `lII-04` · `lII-21` 을 읽는다.
4. 해설(`why`)에서 보기를 **번호로 가리키지 않는다**(①, 「2번」 금지). 보기 글자를 그대로 인용한다.
5. 정답 자리(`answer` 0~3)를 넷에 **고르게** 흩는다. 한 자리가 40% 를 넘으면 검사기가 막는다.
6. 그림 자리는 만들지 않는다 — TOPIK I 15 · 16번, TOPIK II 1 · 2 · 3번.
7. 짝 문항(`type: 'long'`)은 `pair` 이름을 같이 쓰고 **두 문항의 script 가 글자까지 같아야** 한다.
8. 발문에 「남자 · 여자」가 나오면 대본에 그 사람이 꼭 있어야 한다.
9. **도구(`tools/`) · 다른 파일은 고치지 않는다.** `topik-listening.js` 를 손으로 고치지도 않는다 — JSON 으로 내고 아래 도구로 넣는다.

## 밭 (한 문항)

```json
{ "id": "lI-101", "exam": "I", "slot": 17, "grade": 2, "type": "detail",
  "script": [{ "who": "w", "text": "…" }, { "who": "m", "text": "…" }],
  "q": "들은 내용과 같은 것을 고르십시오.",
  "options": ["…", "…", "…", "…"],
  "answer": 2,
  "why": "…" }
```

- `id`: **새 번호대를 쓴다** — TOPIK I 은 `lI-101` ~ `lI-160`, TOPIK II 는 `lII-101` ~ `lII-160`. (지금 있는 id 와 안 겹치게. 한 번 정하면 안 바꾼다.)
- `pair`: TOPIK I 은 `lI-p11` 부터, TOPIK II 는 `lII-p11` 부터.
- `grade`: TOPIK I 은 1 · 2, TOPIK II 는 3 · 4 · 5 · 6.
- `who`: `m` 남자 · `w` 여자 · `n` 안내 방송 · 독백.
- `q`(발문)는 이미 있는 문항의 같은 유형 발문을 그대로 쓴다.

## 몇 개씩

### TOPIK I — 60 (`exam: "I"`)

| 자리(slot) | type | 개수 | grade |
|---|---|---|---|
| 1~4 | reply 알맞은 대답 | 8 | 1 |
| 5~6 | follow 이어지는 말 | 6 | 1 |
| 7~10 | place 여기는 어디 | 8 | 1 |
| 11~14 | topic 무엇에 대해 | 8 | 1~2 |
| 17~21 | detail 내용과 같은 것 | 12 | 2 |
| 22~24 | main 중심 생각 | 6 | 2 |
| 25~30 | long 긴 담화 (짝 6쌍 = 12) | 12 | 2 |

### TOPIK II — 60 (`exam: "II"`)

| 자리(slot) | type | 개수 | grade |
|---|---|---|---|
| 4~8 | follow 이어지는 말 | 8 | 3 |
| 9~12 | act 이어서 할 행동 | 8 | 3 |
| 13~16 | detail 내용과 같은 것 | 10 | 3~4 |
| 17~20 | main 중심 생각 | 10 | 4 |
| 21~50 | long 긴 담화 (짝 12쌍 = 24) | 24 | 4 · 5 · 6 고루 (6급 8개 이상) |

- 자리 번호는 그 유형 칸 안에서 고루 쓴다(예: detail 은 17 · 18 · 19 · 20 · 21 을 섞어서).
- TOPIK II 긴 담화는 인터뷰 · 강연 · 다큐 · 토론처럼 **말하는 장면을 다양하게**. 주제도 겹치지 않게(환경만 여러 개 X).
- 오답 보기는 「대본에 나온 낱말을 쓰되 뜻이 틀린 것」으로 — 낱말만 듣고 고르면 틀리게.

## 소리로 들었을 때 자연스럽게

- 대본은 **입말**로 쓴다(「~거든요」 「~잖아요」 「아, 그래요?」). 읽기 지문처럼 쓰지 않는다.
- TOPIK I 은 한 줄을 짧게(한 줄 25자 안팎), TOPIK II 긴 담화는 전체 4~8줄.
- 숫자 · 시간은 소리 내어 읽기 쉽게 한글로 쓴다(「3시」보다 「세 시」, 「10,000원」보다 「만 원」).
- 괄호 · 따옴표 · 기호(~, /, ※)는 대본에 넣지 않는다 — 기계 목소리가 그대로 읽는다.

## 내는 법

1. 네 묶음(각 30문항)으로 나눠 **JSON 배열만** 파일로 낸다:
   `docs/listening-new-I-1.json` · `docs/listening-new-I-2.json` · `docs/listening-new-II-1.json` · `docs/listening-new-II-2.json`
2. 묶음마다 넣고 검사한다:

```bash
git checkout main && git pull origin main
git checkout -b topik-listening-more
node tools/add-listening.mjs docs/listening-new-I-1.json --dry   # 보기만
node tools/add-listening.mjs docs/listening-new-I-1.json         # 넣기
node tools/check-listening.mjs                                   # 「문제 없음」이 나와야 한다
git add -A && git commit -m "topik listening: TOPIK I 1~30 new"
```

3. 네 묶음 모두 「문제 없음」이면 푸시한다. **자국(stamp)은 찍지 않아도 된다** — Claude 가 main 기준으로 다시 찍는다.
4. 확실하지 않은 문항에는 `"note": "운영자 확인 — 이유"` 를 붙인다(Claude 가 검토하며 지운다).
